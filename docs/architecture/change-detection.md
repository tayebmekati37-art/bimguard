# Change detection (Milestone 4)

Pure, deterministic code in `app/engines/change_detection`. It has no database, network or LLM dependency, so
the same two element sets always give the same ordered list of `Change` records.

## Inputs and matching
Input is two lists of provider-neutral `ElementData` (see `bim.md`). Elements are matched:
1. **By id (GUID).** Confidence base 0.99.
2. **By class and tag**, only for elements left unmatched, and only when exactly one removed and one added element
   share the pair. This recovers elements whose ids were regenerated by a re-export. Confidence base 0.85, and an
   extra low-severity `METADATA_CHANGED` record (`guid`) says the match was not by id.
3. Whatever remains is `ELEMENT_REMOVED` or `ELEMENT_ADDED`.

## What is compared (per matched pair)
| Change type | Detects | Default severity |
|---|---|---|
| `GEOMETRY_CHANGED` | location (distance), rotation (shortest angle), dimensions (`Length`, `Width`, `Height`, `Depth`), body extent | bands: < 100 mm LOW, 100 to 499 MEDIUM, 500+ HIGH (rotation: 1 and 5 degrees); one level higher for structural classes or load-bearing elements |
| `SPATIAL_CHANGED` | room, level | room MEDIUM, level HIGH |
| `PARAMETER_CHANGED` | every property-set and quantity value (added, removed, changed) and material | critical names (`LoadBearing`, `FireRating`, `IsExternal`) and material HIGH; significant names (`OccupancyType`, `PowerKW`, ...) MEDIUM; quantity change of 1% or more MEDIUM; else LOW |
| `CLASSIFICATION_CHANGED` | IFC class | HIGH |
| `METADATA_CHANGED` | element name/tag; revision schema and status (a system-set `superseded` is ignored) | LOW, or MEDIUM for schema change and issue/reject |
| `ELEMENT_ADDED` / `ELEMENT_REMOVED` | no counterpart | MEDIUM; HIGH for structural classes, spaces, load-bearing |
| `REFERENCE_CHANGED` | reserved: document dependency changes, produced in Milestone 5 | n/a |

All numeric comparisons use configurable tolerances (1 mm position and size, 0.1 degree, 0.001 for values), and
differences are rounded before the check so floating-point noise cannot create or hide a change.

## Confidence
`confidence = match base x magnitude factor`, rounded to two decimals. The match base is 0.99 (id), 0.85 (tag).
The magnitude factor is 1.0, or 0.9 when the difference is under 5 times the tolerance (close to measurement
noise). Added/removed elements are 0.97, or 0.80 when an element of the same class was also added and removed, since
that could be a rename. It is a transparent heuristic, not a statistical probability.

## Every threshold is visible
`ChangeDetectionConfig` holds all tolerances, bands, parameter lists and confidence values. A snapshot is stored
with every comparison (`revision_comparisons.config`), so any result can be reproduced and explained.

## Persistence and scale
`revision_comparisons` (one per from/to pair; re-running replaces it) and `detected_changes` (indexed by
comparison, type, severity and tag). The service first compares per-element SHA-256 fingerprints stored at
extraction, and loads full rows only for added, removed and changed elements, so unchanged elements cost one
hash comparison. Comparison runs automatically after a revision is extracted, and can be re-run on demand.

## Limitations
Geometry comparison uses placement, quantity-based dimensions and the extent of rectangular extruded bodies. It does
not diff meshes or B-rep shapes. Severity here describes how significant a change is in isolation; how it
affects other documents is calculated by the impact-analysis engine (Milestone 6).
